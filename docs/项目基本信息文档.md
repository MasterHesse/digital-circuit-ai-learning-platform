## 4. 数据模型（Data Model）

### 4.1 Neo4j 图模型（知识点）

**节点 Label：** `KnowledgePoint`

字段（对应 Java 实体 `KnowledgePoint`）：

- `kpId: String`（唯一 ID，`@Id`）
- `title: String`
- `category: String`
- `difficulty: Integer`

**关系类型：** `:PREREQ`

方向约定：

- `(A:KnowledgePoint)-[:PREREQ]->(B:KnowledgePoint)`
- 含义：A 的前置知识点是 B（A 依赖 B）

---

### 4.2 PostgreSQL

#### 电路仿真存档

##### 表名：`levels`
对应实体：`LevelEntity`

- **主键（PK）**
  - `code` varchar(64) NOT NULL

- **字段**
  - `title` varchar(200) NOT NULL
  - `description` text NULL
  - `template_circuit_json` text NULL
  - `devices` text NULL
  - `allow_cycles` boolean NOT NULL

- **关联/子表**
  - `level_allowed_components`（来自 `allowedComponents`：`@ElementCollection`）
  - `level_kp_ids`（来自 `kpIds`：`@ElementCollection`）
  - `level_test_cases`（来自 `testCases`：`@OneToMany`）

---

##### 表名：`level_allowed_components`
对应实体字段：`LevelEntity.allowedComponents`

- **字段**
  - `level_code` varchar(64) NOT NULL（建议外键 FK -> `levels(code)`；JPA `joinColumns` 指向 `code`）
  - `component` varchar(64) NOT NULL

---

##### 表名：`level_kp_ids`
对应实体字段：`LevelEntity.kpIds`

- **字段**
  - `level_code` varchar(64) NOT NULL（建议外键 FK -> `levels(code)`）
  - `kp_id` varchar(64) NOT NULL

---

##### 表名：`level_test_cases`
对应实体：`LevelTestCaseEntity`

- **主键（PK）**
  - `id` uuid NOT NULL（`@GeneratedValue(strategy = UUID)`）

- **外键（FK）**
  - `level_code` NOT NULL（`@JoinColumn(name="level_code")`，关联 `levels(code)`）

- **字段**
  - `order_index` int NOT NULL
  - `name` varchar(200) NULL

- **唯一约束（UK）**
  - `uk_level_test_case_order`：(`level_code`, `order_index`)

- **关联/子表**
  - `level_test_steps`（`@OneToMany(mappedBy="testCase")`，按 `step_index` 升序）

---

##### 表名：`level_test_steps`
对应实体：`LevelTestStepEntity`

- **主键（PK）**
  - `id` uuid NOT NULL（`@GeneratedValue(strategy = UUID)`）

- **外键（FK）**
  - `test_case_id` uuid NOT NULL（`@JoinColumn(name="test_case_id")`，关联 `level_test_cases(id)`）

- **字段**
  - `step_index` int NOT NULL
  - `inputs_json` text NOT NULL
  - `expected_json` text NOT NULL

- **唯一约束（UK）**
  - `uk_test_step_index`：(`test_case_id`, `step_index`)

---

##### 表名：`level_pass_records`
对应实体：`LevelPassRecordEntity`

- **主键（PK）**
  - `id` bigint NOT NULL（`@GeneratedValue(strategy = IDENTITY)`）

- **字段**
  - `user_id` varchar(128) NOT NULL
  - `level_code` varchar(64) NOT NULL
  - `first_passed_at` timestamptz NOT NULL（Java `Instant`）
  - `last_passed_at` timestamptz NOT NULL（Java `Instant`）
  - `pass_count` int NOT NULL

- **唯一约束（UK）**
  - `uk_level_pass_user_level`：(`user_id`, `level_code`)

## 6. 对外 API 列表与用法

### 6.2 知识点：获取前置知识点（按深度展开）

- Path：`/api/kp/{kpId}/prereqs`
- Query：
  - `depth`：`1..3`，默认 `2`

```bash
curl -s "http://localhost:8080/api/kp/DL-080/prereqs?depth=3"
```

- 200：`List<PrereqDto>`
- 404：起点不存在（Controller 会先 `existsById`）
- 400：depth 越界（`@Min/@Max` 校验触发）

### 6.4 关卡：获取关卡详情

```bash
curl -s http://localhost:8080/api/levels/LEVEL-001
```

- 200：返回关卡详情
- 404：关卡不存在（由 `LevelQueryService`/Repository 决定具体异常映射）

### 6.5 判题：提交电路并判定是否通过

- Method：`POST`
- Path：`/api/levels/{code}/judge`
- Header（可选）：
  - `X-User-Id: <userId>`
- Body：`LevelJudgeApiModels.JudgeRequest`
  - `userId`：可选（与 Header 二选一/覆盖逻辑由 `LevelJudgeService.resolveUserId` 决定）
  - `circuit`：必填（`@NotNull`），任意 JSON（`JsonNode`）

```bash
curl -s -X POST "http://localhost:8080/api/levels/LEVEL-001/judge" \
  -H "Content-Type: application/json" \
  -H "X-User-Id: user-123" \
  -d '{
      "circuit": {
        "nodes": [],
        "wires": []
      }
    }'
```

- 200：返回 `LevelJudgeApiModels.JudgeResponse`
  - `passed`：是否通过
  - `message`：判题信息
  - `failure`：未通过时的失败定位（用例序号、步骤、inputs/expected/actual）
  - `passRecord`：通过记录（`firstPassedAt/lastPassedAt/passCount` 等）
- 400：
  - `circuit` 缺失（Bean Validation 触发）
  - userId 无法解析/缺失（若 `resolveUserId` 有强制要求）

---

### 6.6 判题：查询用户对某关卡的通过状态

- Method：`GET`
- Path：`/api/levels/{code}/pass`
- Header（可选）：`X-User-Id: <userId>`
- Query（可选）：`userId=<userId>`
- Response：`LevelJudgeApiModels.PassStatusResponse`

```bash
curl -s "http://localhost:8080/api/levels/LEVEL-001/pass?userId=user-123"
```

或使用 Header：

```bash
curl -s "http://localhost:8080/api/levels/LEVEL-001/pass" \
  -H "X-User-Id: user-123"
```

- 200：返回是否通过 + `passRecord`（如存在）
- 400：userId 无法解析/缺失（取决于 `resolveUserId` 的实现约束）
- 404：关卡不存在（取决于 Service/Repository 的异常映射）

---

### 6.7 用户：获取用户列表

- Method：`GET`
- Path：`/api/users`
- Response：`List<UserController.UserResponse>`（字段：`userId`, `name`）
- 备注：按 `name` 字典序排序（Controller 里 `Comparator.comparing(AppUserEntity::getName)`）

```bash
curl -s http://localhost:8080/api/users
```

- 200：返回用户列表

---

### 6.8 用户：创建用户

- Method：`POST`
- Path：`/api/users`
- Body：`UserController.UserCreateRequest`
  - `name`：必填（Controller 会 `trim` 后判空）
  - `userId`：可选；不传则后端生成 UUID 字符串

```bash
# 由后端生成 userId
curl -s -X POST "http://localhost:8080/api/users" \
  -H "Content-Type: application/json" \
  -d '{ "name": "Alice" }'
```

```bash
# 指定 userId
curl -s -X POST "http://localhost:8080/api/users" \
  -H "Content-Type: application/json" \
  -d '{ "userId": "user-123", "name": "Alice" }'
```

- 200：返回 `UserResponse`（`userId`, `name`）
- 400：`name` 为空/全空白（抛 `ResponseStatusException(BAD_REQUEST, "name is required")`）
- 409：`userId` 已存在（`CONFLICT`, `"user exists: <id>"`）

## 8. 命名规范

### 8.1 知识点 ID（kpId）

- `kpId`：知识点唯一 ID（Node 主键 / API 路径参数）
- `depth`：前置展开深度（查询参数/DTO 字段；从 1 开始）
- `category`：知识点分类/章节（字符串）
- `difficulty`：难度（整数，范围可后续定义）

示例:
```text
DC-FND-01
DC-BOOL-01
DC-SEQ-04
```

### 8.2 关卡文件（levels）

关卡以 **JSON 文件** 存放（供导入器读取），文件名与关卡 `code` 强绑定，便于排序、定位与防重复。

**命名格式（推荐/当前示例一致）**

- 文件名：`<code>.json`
- `code` 格式：`L<NN>_<SLUG>`
  - `L`：固定前缀（Level）
  - `<NN>`：两位数字序号（`01..99`），用于自然排序与展示（例如章节/关卡顺序）
  - `_`：分隔符
  - `<SLUG>`：关卡短标识，建议使用大写字母、数字与下划线（不含空格），体现主题/目标

**约束**

- 文件名（不含扩展名）必须等于 JSON 内的 `code` 字段值  
  - 例：文件 `L02_XOR.json` 内 `code` 必须为 `L02_XOR`
- `<NN>` 建议保持**递增且不重用**（便于版本迭代时稳定排序）
- `<SLUG>` 应语义明确，避免过长（建议 3～20 字符）

**示例**

```text
L01_AND.json
L02_XOR.json
L03_MUX2.json
L10_FULL_ADDER.json
```
